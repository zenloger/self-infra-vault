# zenlog vault

Хранилище паролей и сертификатов на **https://vault.zenlog.pro**.
Сервер авторизует пользователя через Яндекс и передаёт зашифрованные файлы
из `disk:/secret/*.kdbx`. Браузер открывает и изменяет KeePass-базу локально.
Мастер-пароль, keyfile, записи и вложения не отправляются в API приложения.

## Репозитории

Два независимых Git-репозитория:

```sh
git clone git@github.com:zenloger/self-infra-landing.git
git clone git@github.com:zenloger/self-infra-vault.git
```

Первый содержит сайт-портфолио, второй — это приложение. В Git нет баз KDBX,
паролей, OAuth-токенов, сертификатов с ключами или рабочей конфигурации.
Приватные копии на собственном сервере сохранены в
`/home/zenlog/repositories/zenlog-site.git` и `/home/zenlog/repositories/zenlog-vault.git`.

## Использование

1. Войти через Яндекс и разрешить приложению читать и записывать Диск.
2. Выбрать KDBX из корневой папки `secret` или создать новую базу.
3. Ввести мастер-пароль в браузере; при необходимости выбрать локальный keyfile.
4. Добавить или изменить записи. Сертификаты и ключи хранить как вложения записей.
5. Сохранить: клиент шифрует базу и отправляет только готовый KDBX.

Папки внутри KeePass показаны деревом, включая вложенные и пустые. Выбор папки
показывает её записи, «Все записи» — записи всей базы. Поиск действует в текущей
области, новая запись по умолчанию создаётся в выбранной папке. Переходы по
дереву выполняются локально и не требуют повторного вычисления ключа.

Сложность KDF базы не ограничивается приложением. Во время долгого открытия,
шифрования или объединения видны индикатор ожидания, прошедшее время и кнопка
отмены. Вычисление идёт в отдельном Worker без тайм-аута; исходные параметры
шифрования не ослабляются. Возможность завершить операцию зависит от памяти
устройства и поддержки параметров криптографическим движком.

**Сохранение создаёт новую версию файла**, а не перезаписывает исходник.
В API Диска не документирована атомарная проверка версии при записи;
неразрушающая запись сохраняет обе стороны при параллельной работе в KeePass.
Все версии остаются обычными файлами `.kdbx` в `secret/`. Изменившийся исходник
нужно явно загрузить и объединить на клиенте; невидимой перезаписи нет.

## Подключение Яндекса

Пошаговая настройка: [docs/YANDEX_SETUP.md](docs/YANDEX_SETUP.md).
Нужен зарегистрированный OAuth Client ID и callback
`https://vault.zenlog.pro/auth/callback`. PKCE не требует client secret.
Конфигурация лежит только в `/etc/zenlog-vault.env`, права `0600`.
Без Client ID приложение показывает, что вход ещё не настроен.

## Разработка и сборка

Python 3.11+ и Node.js 22+. Node используется только при сборке клиента.

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
npm ci --ignore-scripts
npm run build
npm test
node scripts/check-bundle.mjs
.venv/bin/python -m pytest server/tests -q
```

`dist/` содержит автономную клиентскую сборку без CDN. Зависимости закреплены
в `package-lock.json`; обновления XML-парсера и распаковщика заданы через
`overrides`, совместимость проверяется KDBX round-trip тестами.

Сервер запускается одним процессом Gunicorn с потоками: OAuth-сессии и токены
хранятся в оперативной памяти и пропадают при перезапуске. Реальные базы
не сохраняются на локальный диск сервера. Systemd и nginx-конфигурация находятся
в `deploy/`; nginx проксирует только на `127.0.0.1:8137`.

## Публикация

Первичная подготовка сервера: Python 3.12 с пакетом `python3.12-venv`, nginx,
Certbot и отдельный сертификат `vault.zenlog.pro`. Для HTTP-01 до выпуска
сертификата предусмотрен `deploy/vault-http.conf`. Для продления используется
общий webroot `/var/lib/letsencrypt` и deploy-hook проверки/перезагрузки nginx.

После `npm ci --ignore-scripts && npm run build` скопировать `dist/` в серверную
рабочую копию `/home/zenlog/zenlog-vault` и выполнить там `bash scripts/deploy.sh`.
Скрипт устанавливает точные серверные версии из `requirements.lock.txt`,
сохраняет существующую конфигурацию OAuth, запускает сервис и проверяет health
до включения nginx-конфигурации. При обновлении исходников используется обычный
`git pull --ff-only`; перезапуск завершает активные OAuth-сессии.

## Граница доверия

[docs/SECURITY.md](docs/SECURITY.md) описывает сессии, CSRF, ограничения путей,
версионирование и клиентскую криптографию. Пользователь всё ещё доверяет
JavaScript, который раздаёт сервер: захват сервера с подменой клиента находится
за пределами гарантии «сервер получает только зашифрованный файл».
Никакие реальные пользовательские секреты не используются в тестах.
