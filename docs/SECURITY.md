# Модель безопасности

Zenlog Vault открывает базы KeePass в браузере. Backend авторизует пользователя
через Яндекс и передаёт зашифрованные `.kdbx` между браузером и Яндекс Диском.
В репозитории находится код приложения, а не пароли, сертификаты, базы или
OAuth-токены пользователей.

## Что получает каждая сторона

| Данные | Браузер | Backend | Яндекс Диск |
| --- | --- | --- | --- |
| Мастер-пароль и локальный key file | Да, при открытии базы | Не отправляются | Не отправляются |
| Расшифрованные записи и вложения | Да, пока база открыта | Не отправляются | Не отправляются |
| Зашифрованный KDBX | Да | Передаёт как двоичные данные | Хранит |
| Имя файла, размер, время изменения и хеш | Да | Да | Да |
| OAuth access token | Не предоставляется клиентскому JS | В памяти процесса | Проверяет при вызове API |
| Идентификатор и логин аккаунта Яндекса | Да | Да | Да |

Мастер-пароль, содержимое записей и файловые вложения не являются параметрами
backend API. Изменения шифруются средствами `kdbxweb` перед отправкой KDBX.
Сертификат с закрытым ключом следует хранить как вложение внутри базы; отдельные
незашифрованные `.pem`, `.key`, `.p12` или `.pfx` на сервер не загружаются.

Это граница штатного протокола, а не гарантия против компрометации сервера:
сервер раздаёт HTML и JavaScript и при захвате может подменить клиентский код,
который обрабатывает мастер-пароль. Доверие к опубликованной сборке, браузеру и
устройству пользователя остаётся необходимым. Приложение не проходило
независимый аудит безопасности.

## Авторизация и область доступа

OAuth Authorization Code использует одноразовый `state` и PKCE `S256`.
После входа создаётся новая сессия. Access token хранится только в памяти
backend; время жизни сессии ограничено восемью часами. Перезапуск процесса
завершает сессии. Refresh token не сохраняется и не используется: после
истечения сессии или отзыва доступа требуется новый вход.

В production используется отдельный origin `https://vault.zenlog.pro`.
Сессионная cookie имеет флаги `Secure`, `HttpOnly`, `SameSite=Lax` и не
распространяется на другие поддомены. Изменяющие запросы требуют проверки
origin и CSRF-токена. OAuth callback является отдельным потоком и проверяет
привязанные к сессии `state` и PKCE verifier.

Для работы с существующим каталогом `/secret` Яндекс выдаёт права
`cloud_api:disk.read` и `cloud_api:disk.write` на весь Диск. Провайдер не
ограничивает этот токен одной произвольной папкой. Backend сам разрешает
только непосредственные файлы `disk:/secret/<имя>.kdbx`, проверяет имена и
фильтрует результаты листинга. Подкаталоги, обход пути и произвольные URL от
клиента не поддерживаются. `cloud_api:disk.app_folder` относится к другой,
специальной папке приложения и не даёт требуемый доступ к `/secret`.

На стороне Яндекса backend использует только фиксированные API endpoints.
Выданные провайдером URL передачи проверяются по схеме HTTPS, порту и
разрешённым hostnames. Каждое перенаправление скачивания проверяется отдельно;
OAuth-токен не передаётся на другой hostname. Загрузка на uploader выполняется
без OAuth-заголовка.

## Сохранение и конфликтующие изменения

Сохранение создаёт новый файл с уникальным именем внутри `/secret`.
Используется `overwrite=false`; исходный файл и предыдущие версии не удаляются.
Новый файл также является обычной базой KDBX, которую можно открыть в KeePass.

Перед сохранением приложение проверяет хеш исходной версии. Если она уже
изменилась, возвращается конфликт. Даже после успешной проверки внешний
KeePass может записать оригинал одновременно с браузером: новый файл сохранит
правки браузера, а оригинал сохранит правки внешнего клиента. Это безопасное
разветвление версий, а не автоматическое слияние и не атомарная замена файла.
При обнаруженном конфликте можно явно объединить исходный файл с открытой
базой в браузере, проверить результат и сохранить новую версию. Для
объединения требуются совместимая база и те же учётные данные KDBX. Сравнение
и синхронизация через KeePass также остаются доступны; история изменений и
резервные версии помогают проверить результат.

KeePass использует время изменения записей при слиянии. Если одна запись
содержит разные данные при одинаковом времени изменения, браузер останавливает
слияние: обе версии нужно скачать и сравнить отдельно. Результат успешного
слияния также следует проверить перед сохранением.

REST API Диска не документирует условную замену по `If-Match` или revision.
Проверка метаданных непосредственно перед `overwrite=true` не устраняет
гонку между проверкой и заменой. Поэтому сервер не выполняет такую замену.
Сериализация запросов одного аккаунта внутри backend не используется как
доказательство блокировки сторонних клиентов.

Сохранение считается подтверждённым после завершения загрузки и сверки
зашифрованных байтов с метаданными провайдера. При неопределённом результате
не следует считать базу сохранённой: нужно сохранить локальную зашифрованную
копию и обновить список файлов. Повтор может создать дополнительную версию,
но не перезаписывает существующие данные.

## Ограничения реализации и эксплуатации

- Размер одного KDBX ограничен 64 МиБ. Лимит проверяется и при приёме, и при
  скачивании; размер зашифрованного файла не ограничивает возможный размер его
  распакованного содержимого.
- Поддерживаются KDBX 3 и 4 в пределах форматов `kdbxweb`. Argon2 выполняется
  локально через `hash-wasm`; старый Argon2 v16 не преобразуется в v19 незаметно
  для пользователя. Приложение не ограничивает сложность KDF: исходные параметры
  памяти, числа проходов и параллелизма сохраняются при открытии и записи.
  Проверяются корректность параметров и возможность их точного представления
  используемым криптографическим движком. Реальная нехватка памяти устройства
  или ограничения движка могут помешать открытию; параметры базы автоматически
  не уменьшаются.
- Мастер-пароль и база обрабатываются в отдельном Web Worker. Длительное
  вычисление показывает индикатор ожидания и прошедшее время без выдуманного
  процента выполнения. Отмена завершает Worker. Во время выполняющейся
  криптографической операции таймер автоблокировки приостановлен; после её
  завершения снова отсчитываются пять минут без действий. Затем Worker
  завершается, интерфейс очищается. Зашифрованная
  восстановительная копия последних успешно подготовленных изменений
  остаётся в памяти страницы; её можно скачать до закрытия вкладки. Текст,
  ещё не применённый в редакторе, в эту копию не входит. Скачайте отдельный
  KDBX, если нужно сохранить работу перед закрытием страницы.
- При блокировке приложения ссылки на расшифрованную базу и поля ввода
  очищаются. JavaScript, WebAssembly, браузер и ОС не дают приложению гарантии
  физического стирания всех копий секретов из памяти. Копирование в буфер
  обмена и скачивание вложения создают копии вне базы.
- Бандлы зависимостей собираются локально из зафиксированного lockfile и
  обслуживаются этим origin. Аналитика и сторонние CDN не нужны. CSP разрешает
  выполнение собственного JS и WebAssembly, а запросы клиента ограничивает
  собственным origin; framing и inline scripts запрещены.
- Не включать debug, HTTP wire logging, дампы запросов, логи Cookie или
  Authorization. URL callback содержит одноразовый OAuth code; подписанные
  download/upload URL тоже являются чувствительными данными. Их нельзя
  включать в access/error logs, скриншоты или отчёты об ошибках.
- `.env`, реальные базы, key files, закрытые ключи и экспортированные пароли
  не коммитятся. TLS-ключ Certbot и optional OAuth client secret находятся
  вне Git. Доступ к конфигурации production ограничивается root.

При подозрении на компрометацию нужно остановить приложение, отозвать доступ
OAuth-приложения в аккаунте Яндекса и проверить развёрнутую сборку. Если во
время инцидента база была открыта в браузере, следует считать возможным доступ
к её содержимому и сменить затронутые учётные данные после восстановления
доверенного клиента.
